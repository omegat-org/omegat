# ADR: Separation of Segment Sorting and Filtering in the Editor

## Status

**Proposed** (Date: 2026-07-23)

- Pull Requests:

    - Sorting hook (`IEditorSorter`): https://github.com/omegat-org/omegat/pull/2161
    - Collapsible bar UI base: https://github.com/omegat-org/omegat/pull/2162
    - Sort bar and sorter model: https://github.com/omegat-org/omegat/pull/2163
    - Numeral parsing foundation: https://github.com/omegat-org/omegat/pull/2154

## Context

Feature request [#1094](https://sourceforge.net/p/omegat/feature-requests/1094/) asks
for a way to sort the segments displayed in the editor, for example alphabetically by
source text, so that translators can group similar segments and translate them in one
pass.

Historically the editor displays segments strictly in their natural project order
(the order in which the filters produced them from the source files). The only
existing mechanism that changes what the editor shows is `IEditorFilter`, which
decides *which* segments are displayed, but not *in which order*. There was no
extension point for reordering.

Implementing sorting inside the filter mechanism was considered and rejected:

- Filtering (selecting a subset) and sorting (permuting the displayed segments) are
  orthogonal concerns. A user must be able to sort without filtering, filter without
  sorting, and combine both independently.
- Folding ordering into `IEditorFilter` would have forced every existing and future
  filter implementation to also deal with ordering.
- Plugins and scripts could not have reordered the editor without replacing the
  active filter.

In addition, parts of the entry navigation assumed that displayed segments appear in
ascending entry-number order (positional lookups), an assumption that any custom
order breaks.

## Decision

Sorting is decoupled from filtering through a dedicated, minimal core hook, with the
sorter model and its UI kept outside the core.

### 1. The `IEditorSorter` interface

`org.omegat.gui.editor.IEditorSorter` is the counterpart of `IEditorFilter`: while
the filter decides which segments are shown, the sorter decides in which order the
already filtered segments are displayed. It exposes a single method:

- **`getComparator()`** returns a `Comparator<SegmentBuilder>` used to order the
  (already filtered) list of segments. Implementations must define a stable, total
  order and should fall back to the natural project order (by entry number) for
  otherwise-equal segments, so that the result is fully deterministic.

The comparator is applied in `EditorController.loadDocument()` *after* filtering.
When no sorter is set, the loading code path is unchanged and the document order is
identical to previous releases.

### 2. API symmetry with filtering

`IEditor` gains `setSort`, `getSort` and `removeSort`, mirroring the existing
`setFilter`, `getFilter` and `removeFilter`. `ConsoleBindings` implements the new
methods, so scripts running in console mode keep working. Plugins and scripts can
therefore reorder the editor without touching the filtering machinery, and vice
versa.

### 3. Scope: per-file ordering

The editor loads one source file at a time, so the comparator only reorders the
segments within the currently displayed file. It does not establish a project-wide
order across files; navigation still moves from file to file in natural project
order.

### 4. Navigation by entry number

Entry navigation locates entries by their exact entry number instead of assuming
positional (ascending) order, so activation, history and neighbour navigation keep
working under any custom order.

### 5. Sorter model and UI outside the core hook

The core only knows the `IEditorSorter` hook. The concrete sorter model and its UI
are delivered separately:

- The sort bar UI and the multi-key sorter model
  (`org.omegat.gui.editor.sort`: `SortBar`, `SortKey`, `MultiKeySorter`,
  `TextKeyComparator`, `NumericValueComparator`, `CachingCollatorComparator`).
- The collapsible bar component (`CollapsibleBar`) that hosts the sort bar without
  taking up editor space when unused.
- Numeric ordering of textual numbers builds on the numeral parsing foundation
  (`NumeralValueParser`).

## Consequences

- With no sorter set, the editor behaves exactly as before; the default code path is
  unaffected.
- Filtering and sorting can be combined freely; neither mechanism needs to know
  about the other.
- Plugins and scripts get a supported way to reorder the editor display.
- Entry navigation is robust under any permutation of the displayed segments.
- Ordering is limited to the currently displayed file; a project-wide order across
  files is out of scope for this design.
- The core commitment is a single small interface; sorting criteria and UI can
  evolve (or be replaced by plugins) without further core changes.
