# ADR: Filter Class Registry Migration to CoreState

## Status
**Proposed** (Date: 2026-08-01)
- Pull Request: [PR#2201](https://github.com/omegat-org/omegat/pull/2201)

## Context
`org.omegat.filters2.master.FilterMaster` held the registry of available filter
classes as a `static` field (`filtersClasses`), mutated through the static
`setFilterClasses(...)`. The `FilterMaster` *instance* (holding the `Filters`
config) already lived in `org.omegat.core.data.CoreState`, but the class registry
remained static global state. Tests set it via `FilterMaster.setFilterClasses(...)`
in `@Before` setup (~8 call sites), so the value leaked across tests, could not be
isolated by `TestCoreState.resetState()`, and was fragile under reordered/parallel
execution — the same static-state testing problem addressed for `Core`
([ADR 2025002](2025002.CoreStateSingleton.md)) and `Preferences`
([ADR 2026002](2026002.PreferencesArchitecture.md)).

## Decision
Move the filter-class registry into `CoreState` so it becomes per-instance,
isolatable application state, following the same testable-singleton seam as
`CoreState` and `Preferences`.

Implementation:
- `CoreState` owns a `filterClasses` list (`CopyOnWriteArrayList`) with
  `getFilterClasses()`/`setFilterClasses()`, following the existing
  `issueProvidersRegistry` pattern.
- `Core` exposes a static facade `getFilterClasses()`/`setFilterClasses()`
  delegating to `CoreState`.
- `FilterMaster` drops its static *field*; its static lookup methods
  (`getFilterInstance`, `addNewFiltersToConfig`) read `Core.getFilterClasses()`.
  The other static utility methods (`createDefaultFiltersConfig`, `loadConfig`,
  `getDefaultSettingsFromFilter`) are unchanged — they simply read the registry
  from `CoreState` now.
- The public static `FilterMaster.setFilterClasses(...)` is **retained as a
  `@Deprecated(forRemoval = true)` method** delegating to
  `Core.setFilterClasses(...)`. OmegaT core has no formal API/SPI boundary and its
  public classes/methods have historically been extended by plugins, so the method
  is deprecated for removal rather than deleted outright; the actual removal will be
  announced on the developer mailing list and performed in a future version.
- Production init (`CommandCommon.initializeApp`) installs the registry via
  `Core.setFilterClasses(PluginUtils.getFilterClasses())`.
- `TestCoreState.resetState()` clears the registry; tests set filter classes via
  `TestCoreState.getInstance().setFilterClasses(...)`.

Production behavior is unchanged.

## Consequences
Filter-class state now follows the same seam as `CoreState` and `Preferences`;
tests are isolated and order-independent, and the static `setFilterClasses(...)`
mutation is removed from all in-repo callers (production init and tests). The
public method is retained, deprecated for removal, so existing plugins keep working
until the announced removal. Filters are still looked up through static utility
methods that read the registry from `CoreState`. The separate
`PluginUtils.getFilterClasses()` discovery list and `Core.registerFilterClass()`
are left unchanged; the resulting dual registry remains pre-existing tech debt,
and unifying it is out of scope.

Test setup for filter-dependent tests is centralized in
`TestCoreState.initFilters(...)`, which registers the filter classes and installs a
`FilterMaster` (from the default or a supplied custom `Filters` config) in the
correct order, replacing the repeated
`setFilterClasses(...)` + `new FilterMaster(createDefaultFiltersConfig())` pair.

## Alternatives Considered
- **Keep the static registry** — leaves the leak and off-pattern static mutation
  in tests.
- **Remove `FilterMaster.setFilterClasses` immediately** — rejected: no formal
  API/SPI boundary means an unannounced removal breaks plugin backward
  compatibility; instead the method delegates to `CoreState` and is deprecated for
  removal, with the removal announced on the developer mailing list beforehand.
- **Also unify the `PluginUtils` registry and route `Core.registerFilterClass`
  through `CoreState`** — larger, touches plugin-loading behavior; deferred.
