# Unified Presentation and Accessibility

## Status
**Proposed** — decision drafted for adoption; refined alongside the ongoing work.

## Date
2026-08-02

## Context

- Segment state and marker information is signalled almost exclusively by colour. Colours are configurable, formatting is not, and non-visual channels do not exist. This violates the "use of colour" guidance of WCAG 2.2 (SC 1.4.1) and shuts out users who cannot rely on colour perception.
- The Swing Accessibility API was essentially unused (no accessible names on panes or icon-only controls) although the JDK bridges it to VoiceOver, Windows UIA/Java Access Bridge and AT-SPI.
- Open tickets point the same way: RFE-1553 (VoiceOver support), RFE-869 (audio hints), RFE-1576 (subtitling workflows), RFE-1321 (per-line counts).
- An AI-simulated persona review (blind, low-vision, deaf/sign-language, motor-impaired translators; 2026-08; no real users were involved — see the appendix for the unabridged statements and for how they were produced) converged on: no information channel may be exclusive; non-focusable controls need reachable equivalents; the active segment is the hotspot (announce it, make it visible, return focus to it predictably).
- Presentation defaults are inconsistently initialised today (see "Default initialisation findings" below), which makes colour behaviour differ per theme, per platform and per load order — a fragile base for any presentation work.

## Decision

OmegaT wants to be accessible.

1. **Use the Swing Accessibility API whenever possible.** Every control, pane and field carries a meaningful accessible name/description; icon-only and non-focusable controls always have a keyboard- and screen-reader-reachable equivalent.
2. **Move towards a multimodal presentation layer.** Information is presented on several sensory channels (colour, text style, shape/frame, sound, speech, and later subtitles/video), and users can direct exactly the channels they need, the way they are most efficient for their individual use case.
3. **One place to configure it.** Colours, text styles and future channels are configured together, per marking, in a single preferences page; no information is ever encoded in one channel only.

## Consequences

### Roadmap (implementation plan)

Each stage is shippable on its own:

- **Stage 0 — Accessibility API baseline** (done in first rounds): accessible names/descriptions for panes, icon-only controls, hint fields, status bar; pane focus shortcuts; keyboard equivalent for the pane gear menu; application-wide editor font zoom.
- **Stage 1 — Text styles per marking** (in progress): bold/italic/strikethrough flags per marking colour entry, edited in the colours table, applied additively so existing view options keep working.
- **Stage 2 — Line styles**: an enum modelled on LibreOffice's `FontLineStyle` (`NONE, SOLID, BOLD, DOTTED, DASHED, WAVE, DOUBLE`) times a position (`UNDER, OVER, THROUGH`), painted by extending the existing `UnderlineFactory`; stored as named strings so later additions stay compatible.
- **Stage 3 — Surround and visual signals**: configurable frame around the active segment (style, thickness, colour); every event signal gets a visual twin (flash, notification history) before or with any audio channel.
- **Stage 4 — Audio, speech and subtitles**: event sounds (with the stage-3 visual twins), optional TTS for proofreading, and the subtitle block with synced video (RFE-1576) building on the previous stages. A glyph halo/buffer (QGIS model) is an optional visibility booster.
- **Option (any stage) — searchable menu commands.** As of current macOS and JDK releases, macOS injects its standard Help-menu search field only into the menu an application registers as `NSApplication.helpMenu`; Swing's screen-menu-bar bridge never registers one and no public JDK API exists, so OmegaT — like virtually every Swing application — lacks it. Two ways to close the gap: (a) register the Help menu natively (JNI/JNA reaching into the AppKit peer; macOS-only and fragile across JDK internals), or (b) a cross-platform "find a command" palette that searches all menu actions and invokes them from the keyboard. Option (b) is the preferred direction: it serves every platform, and it directly answers the keyboard-only persona's reachability-and-discoverability problem (see appendix, motor-impaired translator) — commands that are hard to reach become findable by name.

### Positive

- Markings become distinguishable without colour perception (WCAG 2.2 SC 1.4.1); the style/preview work enables contrast checking (SC 1.4.3/1.4.11) later.
- Screen-reader and keyboard-only operation improves with every stage; nothing is mouse- or colour-exclusive.
- One configuration place reduces today's scatter (colours page, view menu toggles, hidden preferences).
- Per-user channel selection serves efficiency, not only accessibility: audio confirmations for touch typists, strong frames for magnifier users, silence plus flashes for deaf users.

### Negative / costs

- More preference surface: more UI, more persistence keys, more migration paths; the colours table grows columns and later grouping.
- Custom painters (line styles, frames, halo) add rendering code that must stay fast on long segments and correct across look-and-feels.
- The additive overlay deliberately keeps the old "source text bold" view options working, so two sources of truth for bold exist until those options are migrated onto the style flags.
- Audio/TTS/video pull in platform dependencies; they must stay optional (plugin or feature toggle) to keep core lean.
- Upstream review load: the work only lands if cut into small, individually reviewable stages (as listed above).

## Default initialisation findings (research 2026-08-02)

`Styles.EditorColor` initialises its 59 entries in three inconsistent patterns:

1. **17 entries have no default at all** (`null`): among them `COLOR_ACTIVE_TARGET` (while `COLOR_ACTIVE_SOURCE` is themed), all `COLOR_GLOSSARY_*`, `COLOR_MATCHES_DEL_*` (while `COLOR_MATCHES_INS_*` are themed) and `COLOR_MOD_INFO`. Consequences: "unset" is rendered as a red diagonal in the table (colour-only, unreadable for screen readers), reset behaviour differs from themed siblings, and code paths must null-check.
2. **39 entries capture `UIManager.getColor(...)` once at enum load time.** The default freezes to whatever look-and-feel is installed when the class first loads; runtime theme switches (and any code touching the enum before the theme is applied) keep stale defaults until restart.
3. **3 entries use the robust pattern** (UIManager key plus hex fallback): only the project-files progress colours.

Cross-checking the keys the themes define against the keys `Styles` reads exposed dead keys caused by typos in the theme module: it defines `OmegaT.markComesFromTmXendorced` (read: `...Xenforced`), `OmegaT.markComesFromTxXice` (read: `...TmXice`) and the suffix-less `OmegaT.markComesFromTm` (read: `...TmMt`), so these dark-theme defaults never arrive — the likely root cause of SF-1171 (enforced translations losing their background) and the machine-translation marking issues. `OmegaT.markAltTranslations` is read but defined by no theme.

**Consequence for the roadmap:** before or with stage 2, converge all entries on the key-plus-fallback pattern, fix the typo keys, give every entry an explicit, contrast-checked default per light/dark scheme, and add foreground/background pair metadata so contrast can be computed.

## Appendix — persona review, unabridged statements (2026-08-01)

**What "persona" means here.** These statements do not come from real users. They were produced by the AI development assistant: one bot, instructed to split itself into four panellists and argue each perspective in the first person — "schizophrenic" by design — and like all LLM role-play it can hallucinate, so any individual claim may sound lived-in and still be wrong. No lived experience of disability backs these words. The review was a cheap, early way to harvest requirements and priorities; it is not user research and must not be cited as such. Before stages 2-4 solidify, the roadmap should be validated with real users of assistive technologies (for example through the reporters of the accessibility RFEs and the translator communities).

The panel was held in German on 2026-08-01; the statements below are complete, faithful translations. Each simulated panellist was given the quick-win changes and the roadmap draft of this ADR as input.

### Panellist 1 — blind translator (NVDA/VoiceOver, daily screen-reader work)

As a blind translator working with NVDA and VoiceOver every day, here is my statement on the current state:

**1. Which of the quick wins actually helps me?**

The HintTextField fix is the most valuable one: hint text that is read out as if it were field content is a classic trap — I never know whether the field is empty or really contains "enter search term". Also genuinely useful: named icon buttons (previously everything was announced as just "button") and the pane names with live updates, because in OmegaT the title bars often carry counters ("Matches (3)") — if that comes through, it is almost a status display. Rather cosmetic: the accessibleDescriptions taken from tooltips — I rarely read descriptions actively, and long tooltip prose is more annoying than helpful.

**2. The biggest remaining blockers**

- **Segment changes are silent.** When I move to the next segment with Enter, I learn nothing: not the source text, not whether there is a 100% match, not whether there are glossary hits. In memoQ I at least hear the match rate. I would have to jump into four panes with F keys and back every single time — that kills any productivity. Needed: an announcement on segment change (source text + match count/best rate + number of glossary hits), technically e.g. via AccessibleContext property events or a dedicated live region.
- **The editor is one single large text document.** All segments live in one text area; my screen reader sees no difference between source, target, other people's segments and the active segment. I need at minimum: clear boundaries of the editable area and an announcement of the segment status (translated/unreviewed/repeated) — today that is pure colour.
- **Tags inside the segment.** `<t0/>` reads as character salad; whether I have swallowed a tag I only find out during the QA run. Announcing "tag f0 start" and a quick command "check tags in this segment" with a spoken result would be gold.
- **Focus order and reachability:** Matches/Glossary are display panes without real keyboard navigation through individual hits. I want to jump cyclically to hit 1..n and have each read out individually, not receive one lump of text.
- **Tables** (project files, search results, issues): JTable is fundamentally fine with screen readers, but column headers and cell association must be clean, and progress numbers ("57% translated") need to be announceable, not only shown in a status bar that never receives focus.

**3. My top 5**

1. **Segment-change announcement** (source, match rate, glossary hits) — biggest productivity lever; medium effort.
2. **Segment status not only as colour**, but as queryable/announced information in the editor — medium.
3. **Keyboard navigation through match/glossary entries** with individual announcement and insertion via a quick command — medium.
4. **Tag announcement + spoken tag check** — medium to large.
5. **Status bar/progress queryable via a quick command** — small, but needed daily.

**4. ADR stages: audio beeps and TTS**

Beeps: yes, please — short, distinguishable earcons ("no match", "tag error", "save finished") are faster than any speech output and do not interfere with it. That complements the screen reader, it does not replace it. Built-in TTS for segments, on the other hand, is largely redundant for me — I already have a voice that I have configured; a second, competing one would rather be a nuisance. TTS pays off for sighted users (proof-listening) — but then it must be cleanly switchable off. More important than own speech output: offering structured information to the screen reader. Incidentally, the formatting stage (bold/italic instead of colour only) also helps low-vision colleagues with residual sight — do not drop it.

### Panellist 2 — motor-impaired translator (RSI/tremor, almost exclusively keyboard work)

**1. The biggest keyboard blockers**

In my daily work I am blocked above all by: First, mouse-only actions — drag-and-drop docking of the panes simply does not exist for me, likewise title-bar buttons and everything that lives only in the editor's context menu (the context-menu key and Shift+F10 do not work reliably everywhere in Swing). Second, focus loss: after actions like closing the search or confirming a dialog I sometimes do not land back in the editor and have to tab my way through — every additional keystroke costs me real pain, not just time. Third, missing focus shortcuts for panes: I need direct jumps ("focus Matches", "focus Glossary"), not F6 cycles. Fourth, dialogs without mnemonics, without a default button and without Escape behaviour — every modal dialog I cannot leave with Enter/Escape is a small trap.

**2. The gear button with setFocusable(false)**

Fundamentally right — but only half implemented. I do *not* want to stumble through decorative buttons of all title bars while tabbing; a lean tab order is gold for me. But a control may only be unfocusable if the action is reachable some other way. The gear only opens a menu (`menu.show(settingsButton, ...)`) — the right pattern is: the same menu as a menu equivalent (e.g. under "View → Pane settings") plus a shortcut that opens it on the currently focused pane. Then focusable(false) is correct. Without that equivalent it is a real blocker: the function then does not exist for me.

**3. GUI dialog for shortcuts**

Very important — almost existential for me. I have to adapt shortcuts to my hand: chords with many simultaneous modifiers do work with sticky keys but are error-prone; I move them to function keys or single modifiers, and I map Dragon voice commands onto shortcuts. Editing properties files by hand means: researching internal action names, guessing the syntax, restarting, trying things out. A dialog with search, conflict display and "press a key to assign" would be the difference between "works in theory" and "works in practice". Important: list *all* actions there, including the ones shipped without a binding.

**4. My top 5**

1. **Menu/shortcut equivalents for all mouse-only actions** (gear, pane buttons, editor context menu): without that, functions are invisible to me. Effort: medium.
2. **Direct focus shortcuts for all panes** incl. "back to the editor": my most frequent navigation need, hundreds of times a day. Effort: small.
3. **Shortcut editor as a GUI dialog**: the basis for everything else, including voice-input mapping. Effort: large.
4. **Focus discipline**: after every action a defined, predictable focus (usually: back to the segment). Effort: medium, but many small places.
5. **Dialog hygiene**: mnemonics, default button, Escape — consistently everywhere. Effort: small per dialog, medium in total.

In short: first reachability (nothing may be mouse-exclusive), then efficiency (fewer keystrokes), then comfort (remappability).

### Panellist 3 — low-vision translator (approx. 300 % magnification)

**1. Are colours + formatting enough?** No, that is half the battle. The planned formatting per marker category is the single most important point for me — bold/italic/strikethrough I recognise instantly even at 300 % zoom and poor contrast, fine colour gradations I do not. But what is completely missing: **global UI scaling**. The editor font is adjustable; menus, dialogs, the status bar, the "Fuzzy Matches" and "Glossary" windows are not — today I read those with the screen magnifier, and the magnifier constantly costs me the context. In addition: zoom via Ctrl+mouse wheel in the editor (in 2026 I simply expect that), a clearly visible focus marker (the current segment frame and the text cursor are hair-thin under magnification), and guaranteed minimum contrasts in the bundled themes — the default grey tone for untranslated segments is below my perception threshold.

**2. Where colour-as-the-only-channel is worst:** (a) Spelling errors — the red squiggly line is pixel mush at 300 %, I regularly miss errors. (b) Translated vs. untranslated: a delicate background tint, practically invisible for colleagues with red-green deficiency. (c) Search-hit highlighting: a yellow area on a white background, hardly any contrast. (d) MT vs. TM origin of a match — I can only tell those apart if I know which colour means what.

**3. My top 5:**

1. **Formatting per marker category** (medium) — encode information redundantly to colour; benefits everyone, not only me. Already under way, please follow through.
2. **Global font-size scaling of the entire UI** (medium to large) — one factor covering menus, dialogs and all panes; Swing can do it via default fonts, but it must be done consistently. Biggest everyday gain for me.
3. **Focus and cursor visibility** (small) — a wider/configurable text cursor, a strong frame around the active segment. A small intervention, a huge effect under magnification.
4. **Contrast audit of the themes** (small to medium) — check the bundled colour values against WCAG minimum contrast, ship a "high contrast" preset. The colour workstream with theme import/export is the perfect foundation for this.
5. **Ctrl+mouse-wheel zoom in the editor** (small) — quick situational zoom without a settings dialog; I change size several times a day depending on how my eyes are doing that day and on the lighting.

Consistently underlining links I would name as number 6 — right and cheap, but less urgent than the five above.

**4. Audio beeps:** Yes, clearly useful as a second channel — but targeted. A subtle sound on "leaving a segment without a translation" or "tag error on save" would protect me from exactly the errors I miss visually. Important: switchable per event and not chatty, otherwise it is off after an hour. TTS of entire segments I personally do not need — I do read, just laboriously. Priority therefore clearly behind points 1–5.

### Panellist 4 — deaf subtitle translator (team with sign-language interpreters)

**1. Audio feedback (stage 3): no new channel without a counterpart**

Beeps and TTS simply do not exist for me. If OmegaT introduces audio signals, every event that gets a sound must get a visual signal at the same time — not as a retrofit, but as one event abstraction with two output channels. Concretely: a subtle flash of the status bar or the affected segment, a persistent notification icon (so I miss nothing while looking at the video), and a small event history. A flash I do not see in that very second is as useless as a beep. TTS reading of segments does not help me at all; the equivalent would be good visual highlighting of differences (match vs. source) directly in the editor.

**2. Subtitling workplace (stage 4): the minimum**

- **Timecodes visible on the segment** — today, in the SRT filter, I only see naked text and have to keep the timeline in my head.
- **Video preview with subtitle overlay**, driven by clicking the segment (jump to its timecode), loop over the segment duration.
- **CPS/line-length/duration warnings live while typing** (characters per second, max lines, minimum/maximum duration), as configurable rules — that is a craftsman's tool, not a luxury.
- **Instead of a waveform:** for me an audio waveform is worthless. What helps me: the video image itself (I see mouth movement, cuts, speaker changes), a **scene-change marker on the timeline**, and — where available — a visualised transcript along the time axis. A subtitle bar view (segments as blocks on the timeline, overlaps in red) fully replaces the waveform for me.

**3. Sign language in the CAT tool — feasible vs. utopia**

Feasible: for us, German Sign Language (DGS) is target text in video form. Realistic is a workflow "segment → linked video take": per segment a reference to a clip (file + timecode), status "shot/approved". Equally feasible: **linking glossary entries to a sign video** — a field for a video URL/file in the glossary plus a preview in the glossary pane would be gold for teams, because the choice of signs must be consistent. Utopia (today): DGS recognition, automatic translation into sign language, avatars — please, no energy there.

**4. My top 5**

1. **A visual counterpart to every audio event** (flash + notification history) — a question of principle, otherwise stage 3 excludes me. Effort: small–medium.
2. **Timecode display on the segment** for subtitle filters — biggest benefit per effort. Effort: small–medium.
3. **CPS/line-length checking** as a marker/warning — a quality tool for all subtitlers, not only for me. Effort: medium.
4. **Video preview with overlay + segment sync** — the heart of stage 4; without it everything stays flying blind. Effort: large (player dependency, possibly a plugin).
5. **Glossary with sign videos** — a small step, real DGS benefit, and generic (also usable for pronunciation videos and the like). Effort: medium.

A principle to close with: do not think of accessibility as a special stage — every new output (sound, colour, formatting) should be multichannel from the start.
