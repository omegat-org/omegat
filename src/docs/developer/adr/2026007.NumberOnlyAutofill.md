# ADR: Number-Only Segment Auto-Conversion

## Status

**Proposed**: implementation in progress (Slice 1 — the conversion engine — landed).

- Feature request: https://sourceforge.net/p/omegat/feature-requests/794/ ("Auto fill 'number only' segments")
- Builds on ADR 2025002 (CoreState singleton seam) and the numeral foundation branch `topic/stpa/util/numeral-parser`.

## Context

SourceForge RFE #794 asks that segments whose source is *only* a number be filled and marked as translated automatically, so a translator working through a table of numbers does not confirm every cell by hand and so that "skip to next untranslated" (Ctrl+U) passes over them.

The scope was widened during design:

- Apply to **all writing and numbering systems** (Roman, CJK, Arabic-Indic, Devanagari, Ethiopic, full-width, and so on), not just Western digits.
- Parse the value in the **source locale** and re-render it in the **target locale**, so more than bare integers are covered: decimals, grouping, percent, currency, date, time and ordinal.
- Present the work in a dedicated window modeled on the existing **Issues** window: a checklist of data types to include, a scope selector (all segments / current file / current filter), then a results table with columns *Type*, *Original*, *Preview (target)* and an *accept* checkbox (all checked by default, individually deselectable), plus a minimum-confidence threshold.
- Mark applied conversions with a distinct external tag so they are recognizable and skippable.

## Decision

### 1. Numeral foundation reuse

Integer recognition across writing systems is delegated to `org.omegat.util.NumeralValueParser` (ICU-based; the shared `topic/stpa/util/numeral-parser` foundation branch). #794 is its first non-sorting consumer.

### 2. Conversion engine — `org.omegat.util.NumberAutoConverter`

A stateless, GUI-free engine. `convert(source, sourceLocale, targetLocale, types)` returns a confidence-ranked list of `Conversion{type, target, confidence}`; an empty list means the source is not a number-only value of any enabled type.

- **Number-only gate = full consumption.** A type is reported only when a strict parser consumes the *entire* cleaned source. A segment with surrounding prose therefore parses for no type and is out of scope — exactly the ticket's restriction, verified against the demonstration fixture (all 104 prose segments yield nothing).
- **Normalization split.** The source is first cleaned of formatting controls (bidirectional marks, zero-width and no-break spaces) and its whitespace variants folded to a plain space. Numeric types additionally use an **NFKC-folded** form (so full-width digits and percent signs work), but the **ordinal path deliberately uses the unfolded form**, because NFKC destroys the Spanish and Italian ordinal indicator (`º` → `o`).
- **Locale-driven ordinals.** Ordinals are recognized through ICU's rule-based ordinal formatter in the source locale, guarded so a bare digit run is never an ordinal and a parsed value below 1 is rejected. This makes `3.` an ordinal in German but a decimal in English — for free, and correctly.
- **Confidence.** Unambiguous forms score high (INTEGER 0.9, PERCENT 0.85, ISO DATE 0.8); ambiguous ones score low (localized numeric DATE 0.55). Ambiguity is surfaced as multiple candidates rather than resolved silently, which the window's type column and threshold are built to handle.

### 3. Marking (Slice 2)

Applied conversions are registered via `Core.getProject().setTranslation(...)` with a new `TMXEntry.ExternalLinked` value `xNUMBER` (all values of that enum are now documented in place). It is persisted through a new `x-number` TMX property written in the default-translations block and read back in `calcExternalLinkedMode`, gated by `SAVE_AUTO_STATUS` exactly like `x-auto`; without that preference the translation still round-trips but the marking is dropped. It is shown with its own auto-populated marker color (`COLOR_MARK_COMES_FROM_TM_XNUMBER`, defined in both light and dark color schemes) via `ComesFromAutoTMMarker`. Once a translation exists, Ctrl+U skips the segment with no further change. A round-trip test pins both the persisted and the gated-off behavior.

### 4. Window (planned, Slice 3)

Modeled on `org.omegat.gui.issues`: `IssueProvidersSelectorController` → data-type checklist; `IssueChecker`/`IIssueProvider` → scan; `IssuesTableModel`/`IssueColumn` → results table (with an added editable accept column); `IssueDetailSplitPanel` → preview; row click jumps to segment.

## Documented limits

- Ordinals ICU cannot parse in a locale are out of scope: Italian `1º`, Finnish/colon inflected `3:s`, Greek `3ος`, spelled CJK `第三`, French `2ème`. They yield no conversion (characterized by test).
- Scientific notation (`1,5×10³`) is not converted in Slice 1.
- Currency keeps the parsed currency and only re-formats grouping/placement for the target locale; it does not convert between currencies.
- Date rendering uses the target locale's MEDIUM style; the preferred style is an open follow-up.

## Alternatives considered

- **Reuse the round-tripped `origin` property instead of a new `ExternalLinked` value** — less plumbing, but no distinct marker; rejected because a distinct external tag was wanted.
- **A single trailing-punctuation heuristic for ordinals** — rejected after the review below; it is German-centric and breaks across languages.

## Appendix A — critical team review of the ordinal/integer boundary (verbatim)

The following multi-perspective critique was conducted (linguistics, intercultural business communication, internationalization) of an early heuristic — *"reject INTEGER when the last character is not a letter or digit (ordinal marker) → 3. → 3rd"* — and drove the locale-driven redesign above. Reproduced verbatim.

---

## Runde 1 — die Perspektiven

**🗣 Linguistin (Morphologie/Typologie).**
Der Fix setzt zwei stillschweigende Annahmen: (a) Ordinalmarker stehen *hinten*, (b) sie sind *ein* Zeichen. Beides ist sprachübergreifend falsch.
- **Mehrzeichen-Suffixe:** Englisch `1st/2nd/3rd/4th`, Französisch `1er/1re/2e`, Spanisch/Italienisch/Portugiesisch `1.º/1.ª/1.er`, Griechisch `3ος`, Katalanisch `1r/2n/3r/4t`. Dein `ordinalFallback` schneidet aber nur **ein** Zeichen ab (`substring(0, len-1)`) — für „1st" bleibt „1s", Parse scheitert → **englische Ordinalzahlen werden gar nicht erkannt.** Der Fallback ist de-zentriert.
- **Infix/Doppelpunkt:** Finnisch/Schwedisch markieren flektierte Ordinalia mit **Doppelpunkt**: `3:s`, `1:n`, `3:e`. Marker steht in der Mitte, Buchstabe am Ende → weder INTEGER-Ablehnung (endet auf Buchstabe) noch der Ein-Zeichen-Fallback greifen.
- **Präfix-Markierung:** Chinesisch `第三`, Japanisch `第3/3番目`. Der Marker steht **vorn** bzw. ist ein Wort — eine „letztes-Zeichen"-Regel ist strukturell blind dafür.

**🗣 Interkultureller Wirtschaftskommunikator.**
Mein Sorge ist die **Locale-Blindheit**: `3.` wird *unabhängig von der Quellsprache* als Nicht-Integer behandelt. In einer **en→x**-Tabelle ist `3.` aber eher `3.0` (Dezimal) oder schlicht `3`, kein „3rd". Du triffst also eine sprachspezifische Entscheidung (Punkt = Ordinal) global — richtig für de/hu, falsch für en. In Geschäftstabellen (Preise, Ränge, Fußnoten) erzeugt das falsche Auto-Vorschläge, die genau das Vertrauen untergraben, das das Fenster braucht.

**🗣 Internationalisierer (i18n/Unicode/ICU).**
Zwei mechanische Defekte unabhängig von Sprache:
- **RTL & Bidi:** Ein Zahl-Segment kann mit unsichtbaren Steuerzeichen enden — `RLM/LRM/ALM` (U+200F/200E/061C), ZWSP. Die sind weder Whitespace noch alphanumerisch → dein „letztes Zeichen"-Test **lehnt einen sauberen Integer fälschlich ab**. Und `charAt(len-1)` ist das *logisch* letzte Zeichen, im Arabischen visuell das linke — Marker-Position ≠ Codepoint-Ende.
- **NFKC-Reihenfolge-Bug (real, verifizierbar):** Ich mache `source.trim()` *dann* NFKC. `trim()` entfernt kein `U+00A0` (NBSP, > 0x20). NFKC faltet NBSP → normales Space. Ergebnis: `"5 "` → `"5 "` mit **nachlaufendem Space** → letztes Zeichen Space → INTEGER abgelehnt. Fix: NFKC **zuerst**, dann `strip()` (Unicode-Whitespace), plus `Cf`-Steuerzeichen/Default-Ignorables entfernen.
- **Arabisches Prozentzeichen** `٪` (U+066A) fange ich in `tryPercent` gar nicht (nur `%`/`％`).

## Runde 2 — konsolidierte Test-/Defekt-Matrix

| Fall | Quelle | erwartet | aktueller Stand | Defekt |
|---|---|---|---|---|
| en Ordinal | `1st` (en→de) | ORDINAL | **leer** | Fallback schneidet 1 Zeichen |
| fr Ordinal | `1er` | ORDINAL | leer | dito |
| es Ordinal | `1.º`/`2º` | ORDINAL | leer/fragwürdig | dito + NFKC(º→o) |
| fi Ordinal | `3:s` | ORDINAL | leer | Infix-Doppelpunkt |
| zh/ja Ordinal | `第三` | (dokumentiert offen) | leer | Präfix-Marker |
| en Dezimal/Int | `3.` (en→x) | INTEGER/DECIMAL, **nicht** Ordinal | Ordinal-Pfad erzwungen | Locale-Blindheit |
| NBSP-Integer | `5 ` | INTEGER 5 | **leer** | NFKC-vor-trim |
| Bidi-Integer | `5‏` | INTEGER 5 | **leer** | Cf nicht entfernt |
| ar Prozent | `٪٥٠` | PERCENT | leer | `٪` nicht erkannt |
| de Ordinal | `3.` (de→en) | `3rd` | **korrekt** ✅ | — |

Mein Fix „heilt" also nur den de-Fall und führt zugleich neue Fehlklassifikationen ein.

## Runde 3 — empfohlene Korrekturen (Konsens)

1. **Ordinal locale-getrieben statt Zeichenraterei.** Marker aus der **Quell-Locale** ableiten, indem man `RBNF.ORDINAL.format(n)` mit den reinen Ziffern vergleicht → ergibt **Präfix *und* Suffix beliebiger Länge** (z. B. „", „st"; „第", „"). Dann Affixe strippen und den Ziffernkern parsen. Deckt en/fr/es/fi/zh ab.
2. **INTEGER-Ablehnung nur, wenn ein Ordinal *tatsächlich* matcht** (nicht „irgendein Sonderzeichen hinten"). Damit fällt die Locale-Blindheit weg; `3.` in en bleibt Integer/Dezimal.
3. **Normalisierungs-Hygiene:** NFKC **vor** `strip()`; `Cf`/Default-Ignorable-Codepoints (Bidi-Marks, ZWSP) entfernen. Codepoint-sicher (schon via `codePointBefore`).
4. **RTL/Arabisch:** `٪` (U+066A) in `tryPercent`; ICU-Locale-Formatter erledigen `٫`/`٬` selbst.
5. **Mehrdeutigkeit sichtbar machen:** wo `.`/„" sowohl Dezimal als auch Ordinal sein kann, **beide** Kandidaten mit Confidence zurückgeben — das Fenster (Typ-Spalte + Schwelle + Abwählen) ist genau dafür da, statt still zu raten.
6. **Dokumentierte Grenzen** als Tests festschreiben (zh/ja-Präfix, sobald RBNF-Parse scheitert → niedrige Confidence oder leer).

---

*Resolution.* ICU capability was then measured empirically. RBNF ordinal round-trips for en/de/fr/es(with dot)/pt/sv/nl/zh/ja/ca/hu but not for it/el/fi-colon; NFKC was confirmed to break the Spanish/Italian indicator. The engine implements recommendations 1–5 (ordinal parse driven by the source-locale ICU formatter rather than affix guessing, which subsumes recommendation 1's affix approach), and the limits of recommendation 6 are pinned by tests.
